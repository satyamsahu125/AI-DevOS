## Task 29 — Fix usePipeline status_update clears current_stage on partial WS message

### Previous
In `usePipeline.ts`, the `"status_update"` WebSocket message handler updated state as:

```ts
current_stage: (msg.current_stage as string) ?? null,
```

The `??` (nullish coalescing) operator returns the right-hand side only when the left side is
`null` or `undefined`.  A `status_update` message that does not include a `current_stage`
field results in `msg.current_stage === undefined`, so `undefined ?? null` evaluates to
`null` — clearing the active stage from the sidebar.

By contrast, `state` and `stages_completed` both preserve the existing pipeline value when
the field is absent (`?? p.state`, `?? p.stages_completed`).  `current_stage` was the only
field that did not follow this pattern.

The practical effect: any heartbeat or lightweight server-side status update that omits
`current_stage` (because the stage hadn't changed) would blank the pulsing active-stage
indicator in the StageRail until the next `refresh()` REST call (up to 2 seconds later) or
the next `stage_started` WS event restored it.  This is the "briefly de-syncs on WS
reconnect" symptom — `onReconnect` triggers `refresh()` (async REST), and any `status_update`
arriving before the REST response resolved would clear `current_stage`.

### Changed
**`frontend/src/hooks/usePipeline.ts`** — `case "status_update"` handler:

```ts
// Before
current_stage: (msg.current_stage as string) ?? null,

// After
current_stage: "current_stage" in msg
  ? (msg.current_stage as string | null)
  : p.current_stage,
```

The `"in"` operator distinguishes:
- Server sent `current_stage: "architect"` → update to `"architect"`
- Server sent `current_stage: null` → clear to `null` (intentional stage-end signal)
- Server omitted `current_stage` (partial update) → preserve `p.current_stage`

Added an explanatory comment so the intent is clear to future maintainers.

### Next
- Add a unit test for `usePipeline` that sends a `status_update` without `current_stage`
  and asserts the known `current_stage` is preserved.
- Review other WS message handlers for the same pattern — `stage_complete` and
  `stage_started` look correct, but a full audit is worthwhile.

## Task 30 — Expand PYTHON_VERSION_MAP with common agent-requested packages

### Previous
`PYTHON_VERSION_MAP` in `dependency_detector.py` had 24 entries covering the most basic web
stack.  Agents frequently request packages in categories not represented: async DB drivers,
AI/LLM clients, data science, auth helpers, testing extras, and dev tools.  The result was
`# unpinned — add to PYTHON_VERSION_MAP` lines in generated `requirements.txt` for packages
like `asyncpg`, `openai`, `pandas`, `pyjwt`, and others that are nearly universal in modern
FastAPI projects.

### Changed
**`backend/app/workspace/dependency_detector.py`** — `PYTHON_VERSION_MAP`:

Added 37 new entries across 8 categories:

| Category | Packages added |
|---|---|
| Async DB drivers | asyncpg, aiosqlite, motor |
| FastAPI/Starlette extras | python-multipart, email-validator, starlette, gunicorn |
| ORM / data | sqlmodel, tortoise-orm |
| HTTP / networking | websockets, python-socketio, tenacity |
| Auth / crypto | cryptography, pyjwt, authlib |
| AI / LLM clients | openai, anthropic, google-generativeai |
| Data science | pandas, numpy, scikit-learn |
| Templating / utilities | jinja2, python-slugify, arrow, humanize, rich, loguru, structlog |
| Testing extras | pytest-mock, freezegun, factory-boy, hypothesis |
| Dev tools | black, ruff, mypy |

All versions are pinned with compatible-release bounds (`>=X.Y.Z,<N.0.0`) based on July
2026 stable releases.  The `PRICING_LAST_UPDATED` pattern is not replicated here but could
be added as a `PACKAGE_MAP_LAST_UPDATED` constant in a future pass.

### Next
- Add `NPM_VERSION_MAP` entries for common missing packages by the same method (audit which
  npm packages agents request that are not currently pinned).
- Add a CI test: generate requirements.txt from a representative set of imports and assert
  zero `# unpinned` lines for the packages in the map.
- Consider adding a `PACKAGE_MAP_LAST_UPDATED` date constant so engineers know when
  versions were last verified.
